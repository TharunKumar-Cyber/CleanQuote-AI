## Implemented in the branch

- Supabase JavaScript client configured for PKCE, session persistence, automatic refresh, and URL callback detection.
- Account screen supports email/password sign-up, sign-in, sign-out, password recovery, and password update.
- Express bearer-token middleware verifies user identity by calling Supabase Auth `getUser(accessToken)`; it does not trust a decoded token or client-supplied user ID.
- Protected smoke-test endpoint `GET /api/auth/me`.
- Health endpoint reports whether Supabase auth environment variables are configured (never returns key material).
- Minimal identity migration creates `profiles` and `user_roles`, enables RLS, restricts grants, and creates a profile/customer-role record on Auth signup.
- Role assignment is not writable by the signed-in user. Cleaner and admin roles require a separate trusted administrative process.
- Existing quotation extraction remains unauthenticated and unchanged in access requirements for backward compatibility.

## Security notes

- The profile trigger uses user metadata only for a display name; it is never used for authorization.
- A new account receives only the basic `customer` role.
- Users can read their own role rows but cannot insert, update, or delete role assignments.
- The migration's SECURITY DEFINER signup trigger is narrowly scoped and uses an empty search_path with schema-qualified object names.
- The Express endpoint performs an Auth-server lookup for every request. This favours straightforward trusted identity verification for the initial foundation; production load/performance should be measured before considering JWKS verification/caching.
